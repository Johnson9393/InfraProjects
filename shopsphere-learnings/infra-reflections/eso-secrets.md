# ShopSphere — External Secrets Operator (ESO) with AWS Secrets Manager

## 1. Overview

External Secrets Operator (ESO) is a Kubernetes controller that synchronizes secret values from an external secret provider into Kubernetes Secrets. In ShopSphere, AWS Secrets Manager is the external provider, and Kubernetes Secrets are consumed by application workloads.

The goal is to store application secrets in AWS Secrets Manager and let ESO retrieve and refresh them instead of hard-coding secret values into application manifests.

**Current status:** Terraform configuration has been drafted. Formatting, validation, planning, deployment, and live verification are pending.

## 2. What We Have Implemented

- Installed ESO using the Helm chart `external-secrets` from `https://charts.external-secrets.io`.
- Configured Helm to install ESO's CustomResourceDefinitions (CRDs).
- Configured the controller service account as `eso-controller`.
- Added the EKS-managed `eks-pod-identity-agent` add-on to the cluster configuration.
- Drafted an IAM role and a read-only Secrets Manager policy.
- Drafted an EKS Pod Identity association connecting the IAM role to the ESO controller service account.
- Added a `ClusterSecretStore` to configure AWS Secrets Manager as the external provider.
- Added `ExternalSecret` resources to define which AWS secrets to retrieve, which JSON properties to extract, and which Kubernetes Secret keys to create.
- Added the `enable_eso_secrets` variable to enable or disable the application-side ESO resources.

## 3. Terraform Folder Structure and Responsibilities

### `core-infra/cluster/`

This Terraform root creates the foundational AWS infrastructure, including the VPC and EKS cluster.

The `addons.tf` file manages EKS add-ons, including the EBS CSI driver and EKS Pod Identity Agent.

The cluster name follows the environment naming convention:

- Dev: `dev-shopsphere`
- Prod: `prod-shopsphere`

### `core-infra/k8-services/`

This Terraform root manages platform services inside the existing EKS cluster.

- `provider.tf` configures the AWS, Kubernetes, and Helm providers.
- `data.tf` retrieves information about the existing EKS cluster and AWS account.
- `locals.tf` defines environment-specific platform names.
- `eso.tf` creates the ESO namespace and installs the ESO Helm chart with CRDs.
- `eso-iam.tf` creates the IAM role, Secrets Manager read policy, and Pod Identity association.

The ESO controller namespace is environment-specific:

- Dev: `dev-eso`
- Prod: `prod-eso`

The controller's Kubernetes service account is named `eso-controller`.

### `app-infra/`

This Terraform root manages application-specific resources and integrates ShopSphere with ESO.

- `provider.tf` connects Terraform to the selected EKS cluster.
- `data.tf` retrieves the cluster endpoint, certificate, and authentication token.
- `namespace.tf` creates the application namespace.
- `secrets-manager.tf` creates AWS Secrets Manager secrets and stores their JSON values.
- `locals.tf` defines secret mappings, JSON properties, environment-specific names, and secret values.
- `eso.tf` creates the `ClusterSecretStore` and `ExternalSecret` resources when ESO integration is enabled.

The application namespaces are:

- Dev: `shopsphere-dev`
- Prod: `shopsphere-prod`

The ESO controller namespace and application namespace are separate.

## 4. AWS Secrets Manager Secret Structure

The `secrets-manager.tf` configuration names secrets using this pattern:

`<environment>/<secret-name>`

Examples:

- `dev/product-db-credentials`
- `dev/user-db-credentials`
- `dev/redis-credentials`
- `dev/rabbitmq-credentials`
- `dev/payment-service-credentials`
- `prod/product-db-credentials`

Each secret contains a JSON object with properties that ESO can retrieve.

For example, the simplified JSON structure of `dev/product-db-credentials` is:

    {
      "username": "product_user",
      "password": "<generated-password>"
    }

The actual password is generated by Terraform configuration. The values shown here are illustrative; do not store real secret values in this README.

## 5. ClusterSecretStore

`ClusterSecretStore` is an ESO custom resource. It is a Kubernetes configuration object, not a Pod.

Our configuration defines an environment-specific name:

- Dev: `dev-aws-secrets-manager`
- Prod: `prod-aws-secrets-manager`

It specifies the external provider:

    provider = {
      aws = {
        service = "SecretsManager"
        region  = var.region
      }
    }

This tells ESO which AWS service and region to use. The name of the `ClusterSecretStore` is the name of the Kubernetes resource; it is not the name of a secret inside AWS Secrets Manager.

A `ClusterSecretStore` can be referenced by `ExternalSecret` resources across namespaces in the cluster, subject to its configured access controls.

The store configuration does not itself retrieve individual secrets or grant AWS permissions. The controller's AWS identity must be configured separately.

## 6. ExternalSecret

`ExternalSecret` is also an ESO custom resource, not a Pod.

It defines:

- Which `ClusterSecretStore` to use.
- Which AWS secret to retrieve.
- Which JSON properties to extract.
- Which keys to create in the Kubernetes Secret.
- The target Kubernetes Secret name and namespace.
- How frequently ESO should refresh the secret.

Our configuration uses:

    refreshInterval = "1h"

The target uses:

    target = {
      name           = each.value.secret_name
      creationPolicy = "Owner"
    }

This tells ESO to manage the lifecycle of the generated Kubernetes Secret.

The source mapping follows this pattern:

    remoteRef = {
      key      = "${each.value.env_key}/${each.value.secret_name}"
      property = mapping.property
    }

Here, `key` identifies the AWS Secrets Manager secret, while `property` identifies a property inside that secret's JSON value.

## 7. Example: Mapping AWS Secrets to Kubernetes Secrets

Suppose AWS Secrets Manager contains `dev/product-db-credentials` with these properties:

- `username`
- `password`

The `ExternalSecret` mapping specifies:

| AWS JSON property | Kubernetes Secret key |
|---|---|
| `username` | `username` |
| `password` | `password` |

ESO creates or updates a Kubernetes Secret named `product-db-credentials` in the `shopsphere-dev` namespace.

The application can then consume that Kubernetes Secret through its Deployment configuration.

The AWS secret name must match the name created by `secrets-manager.tf`, and every property referenced by `ExternalSecret` must exist in the JSON value.

## 8. How the Secret Reaches an Application Pod

The complete flow is:

1. Terraform creates the secret container in AWS Secrets Manager.
2. Terraform stores the JSON secret value in AWS Secrets Manager.
3. The ESO controller runs in the environment-specific namespace, such as `dev-eso`.
4. ESO reads the `ClusterSecretStore` and `ExternalSecret` custom resources.
5. The controller obtains AWS credentials through the configured EKS Pod Identity mechanism.
6. ESO calls AWS Secrets Manager to retrieve the requested secret.
7. ESO extracts the specified JSON properties.
8. ESO creates or updates the target Kubernetes Secret in the application namespace.
9. A ShopSphere Deployment references that Kubernetes Secret through environment variables or mounted secret volumes.

ESO does not inject secrets directly into a Pod. It synchronizes a Kubernetes Secret, and the application workload must reference that Secret.

**Important:** Environment variables populated from a Kubernetes Secret are generally read when the container starts. Updating the Kubernetes Secret does not automatically update environment variables inside an already-running container; a restart may be required. Mounted Secret volumes are updated eventually, but applications may need to reload the values.

## 9. IAM Permissions and EKS Pod Identity

The drafted IAM policy allows these actions:

- `secretsmanager:GetSecretValue`
- `secretsmanager:DescribeSecret`

The resource ARN is scoped to the selected environment prefix:

    arn:aws:secretsmanager:<region>:<account-id>:secret:<environment>/*

For Dev, the policy targets secrets beginning with `dev/`. For Prod, it targets secrets beginning with `prod/`.

AWS Secrets Manager appends a random suffix to secret ARNs, so the wildcard accommodates that suffix. The secret naming convention must remain consistent with the policy.

The EKS Pod Identity Agent is configured in `core-infra/cluster/addons.tf`.

The association in `core-infra/k8-services/eso-iam.tf` connects the IAM role to the controller's service account:

- Cluster: `dev-shopsphere` or `prod-shopsphere`
- Namespace: `dev-eso` or `prod-eso`
- Service account: `eso-controller`

This lets the ESO controller obtain AWS credentials through EKS Pod Identity.

The role association and policy are configuration only until Terraform is applied. After deployment, verify that the Pod Identity Agent is healthy and the ESO controller can obtain credentials.

If the secrets use a customer-managed KMS key, additional narrowly scoped `kms:Decrypt` permission may be required.

## 10. Environment-Specific Configuration

The same Terraform code is reused for Dev and Prod. The selected environment determines the cluster, namespaces, secret names, IAM role name, and policy scope.

| Component | Dev | Prod |
|---|---|---|
| EKS cluster | `dev-shopsphere` | `prod-shopsphere` |
| ESO namespace | `dev-eso` | `prod-eso` |
| Application namespace | `shopsphere-dev` | `shopsphere-prod` |
| ClusterSecretStore | `dev-aws-secrets-manager` | `prod-aws-secrets-manager` |
| Example AWS secret | `dev/product-db-credentials` | `prod/product-db-credentials` |

Always use the correct environment's variable file and backend configuration. The Kubernetes and Helm providers must connect to the same environment selected for that Terraform run.

## 11. Practical Terraform Commands

Run the commands from the appropriate Terraform root directory.

### Validate `core-infra/cluster`

From `core-infra/cluster/`:

    terraform fmt -recursive
    terraform init -backend-config="vars/dev.tfbackend"
    terraform validate
    terraform plan -var-file="vars/dev.tfvars"

### Validate `core-infra/k8-services`

From `core-infra/k8-services/`:

    terraform fmt -recursive
    terraform init -backend-config="vars/dev.tfbackend"
    terraform validate
    terraform plan -var-file="vars/dev.tfvars"

### Validate `app-infra`

From `app-infra/`:

    terraform fmt -recursive
    terraform init -backend-config="vars/dev.tfbackend"
    terraform validate
    terraform plan -var-file="vars/dev.tfvars"

The `app-infra` root also requires the sensitive variables declared in `variables.tf` to be supplied securely. Do not commit real credentials or secret values to GitHub.

`terraform validate` checks the Terraform configuration and provider schemas, but it does not prove that AWS permissions work, the EKS cluster is reachable, the ESO CRDs exist, or secrets can be retrieved. Plans and runtime verification are still required.

## 12. Recommended Deployment Order

The Terraform roots are separate, so deploy them in dependency order.

1. Apply `core-infra/cluster` to create the VPC, EKS cluster, and EKS add-ons, including the Pod Identity Agent.
2. Apply `core-infra/k8-services` to install ESO and its CRDs, create the IAM role and policy, and establish the Pod Identity association.
3. Apply `app-infra` with `enable_eso_secrets = true` to create the application secrets, namespace, `ClusterSecretStore`, and `ExternalSecret` resources.
4. Verify the ESO controller health and the status of the store and external secrets.
5. Verify that the generated Kubernetes Secrets exist and that application workloads are configured to consume them.

The `ExternalSecret` resources cannot be managed successfully until the ESO CRDs are installed in the target cluster. The Kubernetes and Helm providers also need the target EKS cluster to exist and be reachable.

For a future GitHub Actions pipeline, keep these stages separate and order them according to their dependencies. This avoids trying to manage Kubernetes custom resources before the cluster and ESO CRDs are ready.

## 13. Runtime Verification Commands

After deploying the infrastructure, use the following commands with the correct AWS profile and environment.

Check the Pod Identity Agent add-on:

    aws eks describe-addon --cluster-name dev-shopsphere --addon-name eks-pod-identity-agent --region us-east-1

Check ESO controller Pods:

    kubectl get pods -n dev-eso

Check the ClusterSecretStore:

    kubectl get clustersecretstore
    kubectl describe clustersecretstore dev-aws-secrets-manager

Check ExternalSecret resources:

    kubectl get externalsecret -n shopsphere-dev
    kubectl describe externalsecret product-db-credentials -n shopsphere-dev

Check whether the generated Kubernetes Secret exists:

    kubectl get secret product-db-credentials -n shopsphere-dev

The last command lists Secret metadata, not the secret values. Avoid printing decoded secret values into terminals, logs, or CI output.

If the store or an ExternalSecret reports an error, investigate controller health, AWS identity, IAM permissions, secret names, JSON property names, namespace names, and CRD readiness.
